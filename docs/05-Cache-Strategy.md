# 分布式缓存策略设计与实现

在本项目中，针对高并发场景下的商品详情页（Shop 服务），我们全面引入了 Redis 作为分布式缓存层，并从代码层面针对三大典型并发缓存问题进行了严密防御。

## 1. 缓存穿透 (Cache Penetration)
**场景**：恶意用户不断请求数据库中根本不存在的数据（如频繁请求 `id=-1` 的店铺），导致请求穿过 Redis 直接暴击底层 MySQL。
**解决方案**：**缓存空对象 (Cache Null Value)**。
* **代码实现**：在 `CacheClient.java` 的 `queryWithPassThrough` 方法中。当 Redis 没命中，查 MySQL 也为空时，我们向 Redis 存入一个带有较短过期时间（如 2 分钟）的空字符串 `""`。后续相同的恶意请求会直接命中 Redis 的空值缓存被拦截，保护 MySQL免受冲击。

## 2. 缓存击穿 (Cache Breakdown)
**场景**：一个被极度高频访问的“热点 Key”（例如秒杀爆款商品），在其缓存突然过期失效的瞬间，几十万个并发请求同时打向数据库，瞬间将 MySQL 压垮。
**解决方案**：
我们在系统中并行实现了两种成熟策略供业务灵活调配：
* **策略A：互斥锁 (Mutex Lock)**
  * **代码实现**：`queryWithMutex` 方法。发现缓存失效后，仅允许通过 `setnx` 成功抢占到互斥锁的“唯一一个线程”前往数据库重构缓存。其余未抢到锁的线程则休眠等待重试，从而将对数据库的请求从几十万硬性消减为“1”。
* **策略B：逻辑过期 (Logical Expiration)**
  * **代码实现**：`queryWithLogicalExpire` 方法。我们不再设置 Redis 天然的 TTL，而是在缓存对象的 JSON 中埋入 `expireTime` 字段。每次查到数据后在代码里判断时间。如果过期，当前线程直接返回旧（脏）数据，同时开启异步独立线程池去读取 MySQL 更新缓存。这种极致的 C 端体验保证了响应永远是 0 延迟，适合允许短暂数据不一致的商品页。

## 3. 缓存雪崩 (Cache Avalanche)
**场景**：大批量热点缓存或者系统基础缓存在同一时间点集体过期，或者 Redis 宕机，导致所有流量如同雪崩一样全部涌向 MySQL。
**解决方案**：
* **打散过期时间**：我们在插入缓存时（如 `CACHE_SHOP_TTL`），为其默认的存活时间追加了一个随机数。
* **高可用架构**：后续可在 docker-compose 中升级 Redis 单机架构为 Redis Sentinel（哨兵）或 Cluster 集群模式，保障缓存层本身的绝对灾备存活。
